# Roadmap: Economic Board Game

Продуктовое видение и последовательность развития. Подробные правила описаны в `GAME-BREAKDOWN.md`. Здесь они сгруппированы по этапам. Для каждого этапа указано, что в нём делается на каждом слое системы и какие продуктовые вопросы ещё открыты.

## Видение

Economic Board Game — экономическая настольная игра для 2–6 игроков в браузере. Вдохновлена Monopoly, но имеет собственную финансовую систему.

- **MVP — законченная играбельная игра.** Люди в разных браузерах собираются в комнату и проводят полную партию от старта до победителя. Правила MVP — профиль из GAME-BREAKDOWN. Это классическая по структуре игра, в которой отличаются ценообразование и рента, аукцион и обмены.
- **После MVP** на этот каркас наращиваются новые режимы и механики. Поэтому каркас с самого начала делается расширяемым.
- **Многопользовательская по своей природе.** Каждый игрок — отдельный клиент. Сервер авторитетен, клиент видит только свою проекцию и отправляет только намерения. Каждая механика сразу проектируется с учётом одновременных действий, таймаутов, AFK и скрытой информации.
- **Честность и воспроизводимость.** Каждую партию можно восстановить из лога команд. Будущие броски нельзя предсказать ни по seed, ни по снимку состояния. Повторная доставка команды не удваивает эффект.
- **Точная экономика.** Деньги считаются целыми квантами `Q(x) = 10 × floor(x/10)`. Каждая денежная операция атомарна.
- **Ядро отдельно от инфраструктуры.** Правила живут в чистом детерминированном ядре. Сервер, клиент и боты подключаются к нему как адаптеры.

## Критерии готовности MVP

1. **Партия.** Игрок открывает сайт, входит как гость, создаёт или находит комнату. 2–6 игроков проводят полную партию на `CLASSIC_40` со всеми механиками профиля, и она заканчивается победителем.
2. **Сбои.** Перезагрузка вкладки или обрыв сети не ломают партию: игрок переподключается и продолжает. Рестарт сервера не теряет партии, они восстанавливаются из базы.
3. **AFK.** Бездействующий игрок не может подвесить комнату: на каждом шаге срабатывают таймауты.
4. **Ядро.** Все правила покрыты детерминированными тестами ядра, включая replay.
5. **Развёртывание.** Система разворачивается одной командой.

## Технические решения

| Слой | Решение |
|---|---|
| Ядро правил | `packages/game-core`: TypeScript, чистые функции, без I/O |
| Протокол | `packages/protocol`: схемы сообщений (TypeBox или zod), общие для клиента и сервера |
| Сервер | `apps/server`: Node.js, TypeScript, Fastify, `@fastify/websocket` |
| База данных | PostgreSQL. Лог команд и снимки в `jsonb`, пользователи, комнаты и итоги — реляционно. Доступ через Drizzle или Kysely, без тяжёлого ORM |
| Клиент | `apps/client`: Vite, TypeScript, **Vue 3** для DOM-интерфейса (лобби, панели, диалоги), **PixiJS** для поля, фишек и костей. С этапа визуального дизайна: **Tailwind CSS** для токенов дизайн-системы и **Reka UI** (headless-компоненты) вместо Vuetify; структура клиента по **Feature-Sliced Design** (FSD: app, pages, widgets, features, entities, shared) (решения владельца 2026-11-17) |
| Вход | Гостевой: ник плюс серверная сессия-токен |
| Развёртывание MVP | Docker Compose (сервер и Postgres), один узел |

**Принципы серверной части:**
- **Комната.** Одна комната — один процесс. Команды выполняются последовательно. Сервер подставляет актора из сессии, время и энтропию из CSPRNG.
- **Порядок записи.** Ядро выполняет команду, принятая команда записывается в лог в БД, только после этого изменения рассылаются клиентам. Уникальный индекс `(game_id, revision)` защищает от двух процессов, пишущих одну партию.
- **Восстановление.** Комната поднимается из снимка и хвоста лога. Таймеры пересчитываются по deadline-ам из состояния.
- **Протокол MVP.** На каждое изменение сервер отправляет полную проекцию и события для анимаций. Переподключение — это повторный `Hello` с последней известной revision.

**Не входит в MVP:** Redis и горизонтальное масштабирование, аккаунты и OAuth.

- состояние, команды, события, инварианты;
- сессия с дедупликацией и replay;

## Последовательность развития

Первый этап собирает **сквозной скелет**: все слои системы работают вместе на минимальной игре. Каждый следующий этап добавляет механику сразу во все слои: правило в ядре, сообщения протокола, обработку на сервере, интерфейс на клиенте. После каждого этапа есть играбельная сборка.

```
 1. Скелет насквозь --> 2. Поле и деньги --> 3. Покупка и аукцион --> 4. Рента и постройки
                                                                            |
        +---------------------------------------------------------------------+
        v
 5. Ипотека, долги, банкротство --> 6. Особые клетки --> 7. Обмены --> 8. Доводка MVP
                                                                            |
                                                                            v
                                                                    Расширения после MVP
```

Этапы 6 и 7 не зависят друг от друга, их можно делать параллельно.

### Этап 1 — Сквозной скелет

**Что получаем:** два и больше браузеров входят как гости, собираются в комнату, разыгрывают порядок ходов и по очереди бросают кости. Фишки ходят по полю, таймер хода работает. Экономики ещё нет.

**Ядро:**
- **Порядок ходов.** Каждый бросает одну кость, порядок по убыванию. Ничьи перебрасываются только между собой, начиная с первой нерешённой группы.
- **Ход.** Длится 45 с, бросок — 2d6. Команды игрока принимаются строго раньше deadline, таймаут — в момент deadline и позже. Если броска не было, система бросает сама и даёт 20 с продолжения хода, квоты не сбрасываются.
- **Дубли.** Дубль даёт бонусный ход со свежими временем и квотами. Третий дубль подряд отправляет в тюрьму до перемещения, серия сбрасывается, ход завершается.
- **Квоты хода** (одна постройка, два предложения обмена) пока только как счётчики.
- **Движение** на сумму 2d6 по кольцу из 40 клеток. Раскладка на этом этапе временная, только чтобы фишкам было где ходить. Настоящая появится на этапе 2.

**Протокол:**
- `Hello`, `Welcome`, `Command`, `Ack`, `Update`;
- коды ошибок;
- версия протокола.

**Сервер:**
- гостевой вход;
- лобби: создать, войти, начать;
- комната, исполняющая команды;
- WebSocket;
- таймеры, отправляющие `Timeout`;
- запись лога и снимков в Postgres, восстановление комнаты после рестарта;
- переподключение клиента.

**Клиент:**
- Vue: экраны входа и лобби, HUD с порядком ходов и таймером;
- PixiJS: кольцо поля, фишки, анимация костей и перемещения.

**Инфраструктура:**
- Docker Compose;
- миграции БД;
- скрипты сборки и запуска.

**Решения владельца (приняты 2026-11-14):**
- **Таймаут в setup.** На бросок за порядок даётся 45 с. По истечении система бросает за игрока.
- **Временное правило тюрьмы (без денег).** Заключённый в каждый из своих следующих ходов, максимум три, пытается выбросить дубль. Дубль освобождает, и игрок ходит на выпавшую сумму. Бонусного хода такой дубль не даёт. После третьего неудачного броска игрок выходит и ходит на сумму этого броска. Правило помечено в коде и протоколе как временное и заменяется на этапе 6.
- **Дубль при автоматическом броске.** Даёт бонусный ход после завершения текущего хода и обязательного расчёта, как принято в GAME-BREAKDOWN.
- **Бездействие после броска.** По deadline хода система выполняет обязательные расчёты и закрывает ход.
- **Лобби.** В комнате от 2 до 6 участников. Партию начинает создатель комнаты, когда в ней не меньше двух участников.
- **Поиск комнат.** Все комнаты видны в публичном списке лобби. Создатель может задать код доступа: тогда войти можно только по коду или по ссылке-приглашению, содержащей код. Комнату без кода может занять любой из списка, пока есть места.
- **Выход до старта.** Участник может выйти из комнаты до начала партии. Если выходит создатель, комната закрывается.
- **Выход во время партии = сдача.** Игрок, явно покинувший партию, сдаётся и навсегда выбывает: он убирается из порядка ходов, его незавершённый ход закрывается. Если остаётся один активный игрок, он побеждает. Обрыв связи сдачей не считается: игрок может переподключиться, а пока его нет, действуют таймауты. С появлением экономики (этап 5) активы сдавшегося возвращаются банку свободными, как при банкротстве перед банком.

**Открытых продуктовых вопросов нет.**

### Этап 2 — Поле и деньги

**Что получаем:** настоящее поле `CLASSIC_40` с активами и ценами, у игроков есть деньги, за проход старта выплачивается награда.

**Ядро** (GAME-BREAKDOWN, разделы «Участники и поле», «Начальная настройка и деньги», «Движение, круг и награда»):
- **Структура поля:**
  - 22 обычных актива в группах `2 + 6×3 + 2`;
  - 4 count-based актива;
  - 2 dice-based актива;
  - старт, тюрьма, казино, «в тюрьму»;
  - 8 клеток шанса.
- **Поле** генерируется при создании партии и хранится вместе с версией генератора. Цены фиксированы на всю партию.
- **Стартовый капитал** одинаков для всех: `C = Q(α × S / N)`, ориентир `α = 600/569`. Отрицательные балансы запрещены.
- **Награда за круг** `Q((2/15) × C)` выплачивается при движении вперёд через старт, включая точное приземление на него. При движении назад и при переводе в тюрьму награды нет.

**Протокол, сервер, клиент:**
- поле в проекции;
- балансы игроков;
- PixiJS: клетки с названиями, группами и ценами;
- Vue: панель игроков с балансами, карточка актива.

**Решения владельца (приняты 2026-11-14):** каталог, формула цен, раскладка, генерация наполнения и порядок награды и расчёта на клетке — в `docs/proposals/stage-2-asset-catalog.md`.

**Открытых продуктовых вопросов нет.** Кредитный лимит не входит в MVP (решение владельца 2026-11-14), он перенесён в расширения.

### Этап 3 — Покупка и аукцион

**Что получаем:** свободный актив можно купить или выставить на аукцион, в котором участвуют все игроки одновременно.

**Ядро** (раздел «Покупка и аукцион»):
- **Варианты при приземлении:** покупка по фиксированной цене или аукцион. Если время вышло без покупки, автоматически начинается аукцион.
- **Ставки:** стартовая 60% цены, шаг 5% (обе квантованы). Первая ставка равна стартовой, каждая следующая — ровно текущая плюс шаг: одно действие «Поднять», сумму не выбирают (решение владельца 2026-11-16).
- **Очерёдность:** круговая, первым отвечает приземлившийся игрок. Пас необратим. Лидер не перебивает сам себя. На ответ 10 с, молчание считается пасом.
- **Блокировки:** средства лидера резервируются, конфликтующие действия заблокированы, таймер хода на паузе.
- **Итог:** аукцион без ставок оставляет актив свободным.
- **Сдача во время покупки или аукциона** (решения владельца 2026-11-16):
  - сдался участник, который не лидирует, — это пас;
  - сдался лидер — лидером снова становится предыдущая по величине ставка (её деньги снова резервируются), аукцион продолжается с этого места; если более ранних ставок нет — со стартовой цены; сдавшийся ничего не платит;
  - это верно, даже если автор предыдущей ставки уже спасовал: его ставка остаётся обязательной, он снова лидер, но больше не отвечает и выигрывает, если остальные спасуют;
  - сдался приземлившийся игрок до выбора между покупкой и аукционом — аукциона нет, актив остаётся свободным;
  - аукцион, открытый сдавшимся игроком, доигрывают оставшиеся, затем его ход закрывается.

**Протокол, сервер, клиент:**
- ставки — первые одновременные команды разных игроков, они защищены по цели «аукцион»;
- Vue: диалог покупки, панель аукциона с таймером ответа;
- PixiJS: отметка владельца на клетке.

**Открытых продуктовых вопросов нет.**

### Этап 4 — Рента и постройки

**Что получаем:** владение активами приносит доход, на полных группах можно строить.

**Ядро** (раздел «Активы, рента и строительство»):
- **Обычные активы:**
  - без домов рента 5% цены, при полной группе — удвоенная;
  - с 1/2/3/4 домами — 15/35/65/100% цены.
- **Count-based активы:** при 1/2/3/4 незаложенных владениях — 5/10/20/40% цены того актива, на который встали. Дома не строятся.
- **Dice-based активы:** `groupMeanPrice × сумма костей / 200 × activeHoldings`. Дома не строятся.
- **Строительство:**
  - дом стоит 50% цены актива, максимум 4;
  - нужна полная группа без ипотек;
  - строить и продавать равномерно;
  - не более одного нового дома за ход.

**Протокол, сервер, клиент:**
- Vue: управление постройками;
- PixiJS: дома на клетках, анимация выплаты ренты.

**Решения владельца (приняты 2026-11-16):**
- Если игрок встал на свой актив или рента равна нулю, расчёт закрывается автоматически: ничего не платится, подтверждение не нужно.
- Удвоение ренты полной группы сохраняется, даже если один из активов группы заложен. Заложенный актив сам ренту не приносит. Строить по-прежнему можно только на полной группе без ипотек.
- Не больше одного нового дома за ход. Дополнительный ход за дубль считается отдельным ходом: в нём можно построить ещё один дом.
- Временно, до этапа 5:
  - если на ренту не хватает денег, игрок отдаёт всё, что есть, остаток списывается;
  - активы сдавшегося игрока ренту не приносят;
  - если плательщик или владелец сдался до оплаты ренты, рента не платится.

**Открытых продуктовых вопросов нет.**

### Этап 5 — Ипотека, долги, банкротство и конец партии

**Что получаем:** при нехватке денег система сама находит наименее болезненный способ расплатиться. Если расплатиться невозможно, игрок выбывает. Побеждает последний оставшийся. **С этого этапа партию можно доиграть до конца.**

**Ядро** (разделы «Ипотека и расчёт долгов» и «Банкротство»):
- **Ипотека:**
  - аванс `Q(50% цены)`, погашение ровно на сумму аванса;
  - заложить можно только актив без домов, заложенный актив не приносит ренту;
  - продажа дома даёт `Q(50%)` цены постройки;
  - закладная и её срок переходят вместе с активом.
- **Автоликвидация** (решение владельца 2026-11-17, заменяет поиск минимальных потерь):
  - хватает наличных — платим только ими;
  - если наличные плюс продажа всех домов плюс залог всех активов меньше долга — сразу банкротство;
  - иначе по шагам, пока денег не хватит: залог активов вне полных групп → залог активов полных групп без домов → продажа домов равномерно, голый актив сразу закладывается;
  - внутри шага первым идёт актив с наименьшей рентой, при равенстве — более дешёвый; дома сначала продаются в группе с наименьшей рентой;
  - все логистики или обе энергетики игрока считаются полной группой;
  - пока у игрока открыта рента, он может сам заложить актив или продать дом.
- **Банкротство при одном кредиторе:**
  - кредитору перечисляется `min(долг, cash + proceeds)`, остаток списывается;
  - дома удаляются, ипотеки очищаются, активы возвращаются банку свободными;
  - связанные предложения отменяются;
  - игрок навсегда выбывает.
- **Победа:** побеждает последний активный игрок.

**Протокол, сервер, клиент:**
- итоги партии сохраняются в БД;
- Vue: ипотека и погашение, экран выбывания, экран итогов партии.

**Решения владельца (приняты 2026-11-16):**
- Заложить можно только актив без домов: сначала игрок продаёт постройки.
- Срок ипотеки — 8 коллективных кругов. Один коллективный круг завершается, когда каждый активный игрок сделал по одному ходу.
- Если актив не выкуплен до конца срока, он становится свободным (возвращается банку). Полученный аванс остаётся у игрока, долга не возникает.
- Кредитных механик в MVP нет. Каждый обязательный платёж рассчитывается сразу, поэтому у игрока в любой момент не больше одного кредитора. Многокредиторные долги в MVP не возникают.

**Открытых продуктовых вопросов нет.**

### Визуальный дизайн (после этапа 5, решение владельца 2026-11-17)

**Что получаем:** все готовые экраны переведены на дизайн владельца, поэтому интерфейс этапов 6 и 7 сразу делается в новом стиле.

- Макет: `docs/design/ui-mvp-v1.html` (числа в нём показательные); бриф: `docs/design/ui-brief.md`.
- Дизайн-система из макета: цвета, градиенты групп и игроков, шрифты Unbounded и Inter.
- Первой задачей подключаются Tailwind CSS (токены дизайн-системы) и Reka UI (диалоги, всплывающие окна, подсказки, вкладки); точные версии выбирает Team Lead.
- В той же первой задаче клиент перестраивается по Feature-Sliced Design (FSD). Поле на PixiJS — отдельный виджет. Раскладку по слоям выбирает Team Lead.
- Экраны: вход, лобби, комната ожидания, игровой экран с журналом и чатом, покупка, аукцион, карточка актива, рента и долги, залог, выбывание, итоги.
- Логотипы компаний на клетках (файлы рядом с каталогом).
- Мобильная версия — по отдельному макету, когда владелец его пришлёт.
- Из этапа 8 сюда переходит визуальная часть; журнал событий и чат делаются здесь.



**Что получаем:** казино, шанс и полноценная тюрьма.

**Ядро** (раздел «Особые клетки и события»):
- **Казино:** необязательная ставка один раз за приземление, максимум 10% стартового капитала, шанс 50%. Выигрыш равен ставке, проигрыш забирает ставку. Нельзя играть, пока не закрыт обязательный платёж.
- **Шанс:** случайно ±5% или ±10% стартового капитала, равновероятно.
- **Тюрьма:** клетка «в тюрьму» и окончательные правила выхода, по ответу на вопрос из этапа 1. Временное правило из этапа 1 заменяется.

**Клиент:** диалог казино, анимация карты шанса, состояние «в тюрьме».

**Решения владельца (приняты 2026-11-16), окончательная тюрьма:**
- В течение до трёх своих ходов заключённый пытается выбросить дубль; дубль освобождает, игрок ходит на сумму костей.
- До броска можно выйти добровольно, заплатив банку плату за выход.
- После третьего неудачного броска игрок платит плату за выход и ходит на сумму этого броска.
- Плата за выход — `Q(награда за круг / 4)`: 990 / 660 / 490 / 390 / 330 для 2–6 игроков (ориентир владельца: 500 при капитале 15 000).

**Открытых продуктовых вопросов нет.**

### Этап 7 — Обмены

**Что получаем:** двусторонние предложения обмена активами и деньгами между игроками, в том числе вне своего хода.

**Ядро** (раздел «Обмены/предложения»):
- **Создание:** только в свой ход, максимум два за ход.
- **Срок:** 90 с. Инициатор может отменить предложение. Оно переживает смену хода.
- **Принятие:** в любой ход до истечения срока. При принятии владение, средства и ограничения перепроверяются, затем всё передаётся атомарно или не меняется ничего.
- **Один актив** может участвовать в нескольких предложениях. Конкурирующее предложение не может потратить деньги повторно.
- **Видимость:** содержимое предложения видят только его участники. Это первая скрытая информация в проекции.

**Клиент:** конструктор предложения, входящие предложения, принятие и отказ.

**Решения владельца (приняты 2026-11-16):**
- Статусы предложения: «ожидает», «принято», «отклонено», «отменено». Истечение срока — это «отклонено». «Отменено» — инициатор отозвал предложение сам.
- Пока у игрока не закрыт обязательный платёж, обмены ему недоступны.
- Заложенный актив можно обменять: ипотека и её срок переходят вместе с активом. Актив с домами в MVP обменять нельзя.

**Открытые вопросы:**
- Модель предлагаемого набора.
- Полная матрица правил принятия вне своего хода.

### Этап 8 — Доводка MVP

**Что получаем:** игра готова для реальных людей.

- **Устойчивость:**
  - переподключение в любой фазе, включая аукцион и обмены;
  - восстановление всех активных комнат после рестарта сервера;
  - проверка на обрывах сети.
- **AFK и выход из комнаты.** Что происходит с игроком, который ушёл навсегда.
- **Интерфейс:** журнал событий партии, понятные сообщения об отклонённых действиях, базовая адаптивность.
- **Решения владельца (приняты 2026-11-17):** визуальный стиль свой, с градиентами, между тёмной и светлой темой; на клетках логотипы компаний (проверка товарных знаков до публичного релиза); чат игроков в партии внутри журнала событий. Ориентиры и описание — `docs/design/ui-brief.md`.
- **Эксплуатация:** конфигурация окружений, логирование, health-check, инструкция по развёртыванию.
- **Нагрузочная проверка:** заданное число одновременных комнат на одном узле.

**Открытые вопросы:**

## Расширения после MVP

Порядок не определён. Перечень:

- **Новые режимы игры** на базе того же ядра.
- **Экономика:** кредитная система и динамические проценты; IPO, акции, дивиденды и контроль владения.
- **Карты:** полный каталог шансов, многокредиторные эффекты.

- **Масштабирование:** горизонтальное масштабирование серверов (Redis для маршрутизации комнат и pub/sub).
- **Боты** для игры против компьютера и для замены выбывших игроков.
- **Мобильное приложение:** упаковка веб-клиента через Capacitor. Клиент остаётся на Vue (решение владельца 2026-11-17): ядро и протокол и так не зависят от фреймворка, а поле на PixiJS в React Native не переносится.
- **Баланс:** симуляции для балансировки каталога и правил.
